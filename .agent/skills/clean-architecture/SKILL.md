# 🏗️ Clean Architecture & Decomposition

Этот свод правил регламентирует, как код должен быть разделен на слои, файлы и модули, чтобы проект мог безопасно масштабироваться. Это финальный уровень Enterprise-разработки.

## 1. Локализация и Тексты (Dictionaries)
Строгий запрет на хардкод пользовательского текста (заголовки, кнопки, уведомления) внутри JSX-файлов.
- **Единый источник истины:** Весь UI-текст выносится в отдельные словари (Server Dictionaries).
- **Структура словаря:** Словари хранятся в папке `@/dictionaries/` и разделены по доменам (например, `orders.ts`, `common.ts`).
- **Применение:** Импортировать словари в компоненты (`import { ordersDict } from '@/dictionaries/orders'`).

## 2. Системные константы и Конфиги (No Magic Values)
Запрет на "магические числа" и строки в бизнес-логике.
- **Файлы констант:** Лимиты пагинации, дефолтные налоги, ключи `localStorage` выносятся в файлы `constants.ts` рядом с фичей или в глобальный `@/config/app.config.ts`.
- **Именование:** Использовать `UPPER_SNAKE_CASE` для глобальных констант (например, `ORDERS_PAGINATION_LIMIT`).

## 3. Слоистая архитектура (Service Layer)
Запрет на смешивание маршрутизации (Route Handlers/Server Actions) с базой данных.
- **Слой контроллера (Server Actions):** Отвечает ТОЛЬКО за прием данных, авторизацию и валидацию (Zod).
- **Слой сервиса (Business Logic):** Вся работа с базой данных (Prisma) и сложная бизнес-логика выносится в отдельные классы/функции в папку `@/services/` (например, `OrderService.ts`).

## 4. Дробление компонентов (Container/Presenter)
Ни один UI-файл не должен превышать 150-200 строк.
- **Server Components (Containers):** Отвечают за фетчинг данных. Не имеют стилей (только базовый layout).
- **Client Components (Presenters):** Получают готовые данные через `props`. Отвечают за Glassmorphism, Framer Motion и интерактивность.
- **Вынос подкомпонентов:** При сложной вложенности JSX (>3-4 уровней) логические блоки (шапка таблицы, строка) выносятся в папку `_components` рядом со страницей.
